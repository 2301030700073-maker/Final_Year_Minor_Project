# Low-Level Design — Core Phases 1-4

Concrete, implementation-ready design for the deterministic core. Phases 5-7 stay at the high-level-architecture level of detail until this core is proven and each AI phase's own low-level design is written immediately before it starts (ADR-0003) — writing their low-level design now would be speculative.

The remaining work is organized by *detection surface* per ADR-0008 (technology-based reorganization). This doc specs the deterministic groups — the expanded static core, native `.so` analysis, and the coverage/measurement layer — as implementation-ready design. The gated groups (dynamic bypass synthesizer, AI baseline + learner) are deferred: their own low-level design is written immediately before each starts (ADR-0003), and the synthesizer's execution stays behind the sandbox + human-review gate (ADR-0004) with the AI learner's promotion gated on an empirical baseline diff (ADR-0008).

## WSL2 → Windows Frida bridge (added after real testing on the reference machine)

Windows' ADB server and a Windows-managed emulator's `frida-server` are both only reachable on Windows' own `127.0.0.1`, which WSL2 cannot address directly, and `netsh portproxy` conflicts with `adb forward`. `device.py` resolves this with a small relay: `adb forward` sets up a Windows-local listener, a Python relay process (`scripts/frida_relay.py`) is started on Windows (via `Start-Process` from WSL2) bridging that listener to a port reachable from WSL2 over the Windows host IP, and Frida connects through `add_remote_device()` to that relay instead of `frida.get_device()` directly. `device.setup_frida_connection()` is a no-op passthrough to `frida.get_device()` on native Linux - this whole bridge only activates when actually running under WSL2. Real bugs found and fixed in the first version of this (verified by direct testing, not assumed): a hardcoded personal-machine fallback where Windows-user-directory detection should instead fail loudly; `Get-Process`-based cleanup that never actually matched anything since `CommandLine` isn't populated without elevation (needs `Get-CimInstance Win32_Process` instead); a blind `sleep(3)` replaced with an actual poll-until-listening check.

## Signature YAML schema

```yaml
- id: root_su_binary_check
  category: root
  weight: 0.3
  pattern_type: string_literal   # string_literal | class_reference | regex (native adds export_symbol | embedded_string)
  patterns:
    - "/system/bin/su"
    - "/system/xbin/su"
  evidence_type: bytecode_string

- id: rootbeer_framework
  category: root
  weight: 0.5
  pattern_type: class_reference
  patterns:
    - "com.scottyab.rootbeer"
  evidence_type: bytecode_class
```

Each matched signature contributes its `weight` to a running confidence score per category (`root`, `ssl`), capped at 1.0. Every match records `{signature_id, file, line_or_offset, matched_text}` as evidence — this satisfies FR-2.2/FR-2.3/FR-2.6 and NFR-16 directly: no finding without a citation.

## Decision engine interface

```python
def classify(static_evidence: StaticEvidence) -> ClassificationResult:
    """Deterministic weighted-signature scoring.
    Returns per-category confidence + the full evidence list behind it.
    The default (DEFAULT_THRESHOLD = 0.7) lives in decision_engine.py, not
    settings.yaml - callers may override per call. settings.yaml may carry a
    copy for CLI wiring, but the engine symbol is the source of truth (G8).
    """
```

`ClassificationResult` carries `action: ROOT_ONLY | SSL_ONLY | BOTH | NEITHER`, per-category confidence, and the evidence list — everything the report and the calibration recorder need, with nothing hidden behind an opaque score (FR-3, ADR-0001).

## Deterministic roadmap groups (ADR-0008, spec'd here)

These extend the deterministic core; all remain signature/rule work under ADR-0001. Native matches and behavioral indicators are additional *evidence sources*, not a separate decision tier — they feed the same weighted-confidence model.

### Expanded static core
- **Obfuscation indicator** — a per-run `obfuscation_level ∈ clear | light | heavy`, derived by one concrete deterministic rule (G7): ratio of single-char class identifiers among decompiled classes — `> 0.40` → `heavy`, `> 0.10` → `light`, else `clear` (the single-char ratio is a stable, cheap proxy for minified/obfuscated names). N3: the thresholds are validated by manual inspection against the known corpus, not "tuned in calibration" — calibration has no obfuscation dimension (`GroundTruthEntry` carries only root/ssl/source); an automated calibration tuning pass is deferred until one exists, so this text promises no loop that isn't there. N1: `heavy` forces the Java surface's coverage to `partial` in the coverage contract (G1) — a heavy target's strings are encrypted/reachable only via decryptors, so a clean NEITHER is not proof of absence and must not certify as a confident TN. Reported, not used to silence findings for `clear`/`light`.
- **Behavioral indicators** — narrowed (N2): reflection-based string building and crypto primitive usage are already covered by the existing `class_reference`/`regex` matcher, so they need no new machinery. The one structurally loose case is **string-decryptor stubs**, which is a data-flow pattern a single-line text match can only weakly approximate. Scoped honestly: decryptor-stub detection is marked `partial` in the coverage contract (G1) — it contributes evidence when a stub is found, but a decryptor-stub *absence* is never treated as proof that strings are not decrypted (the `heavy` obfuscation rule above already forces that surface to `partial`). A real data-flow capability for decryptor-stub detection is deferred, not promised.
- **Manifest / resource analysis** — beyond the existing `network_security_config` read: stored-cert presence, `DevicePolicyManager` usage, and the networkSecurityConfig element itself, matched against the signature set. Every read carries its own coverage state.
- **No silent parse swallows** — every unparseable manifest/resource element surfaces as a `parse_failure` rather than being skipped; a partial parse never presents as a complete scan (G9). Because the current parser is `xml.etree.ElementTree` (`static/manifest.py`), which exposes no element byte offsets and hard-fails the whole document on malformed XML, `parse_failure` is specified as a **coverage-state driver**, not a byte-offset promise: a manifest that fails to parse (or whose resources partially fail) drives its surface to `partial`/`unscannable` in the coverage contract, which is what actually prevents a confident negative. An optional position-aware upgrade (e.g. `lxml` `sourceline`) may add byte offsets later; it is not a precondition for the guarantee that nothing is silently skipped.

### Native `.so` analysis (`static/native.py`)
Parses `.so` export symbols and embedded strings from each native library in the APK, matched by hand-authored native signature rules in `config/signatures/native_detection.yaml`. Matches record the same `{signature_id, file, line_or_offset, matched_text}` evidence shape and contribute weight to the same per-category confidence — so native root-detection or SSL-pinning logic is scored identically to Java-side logic, and the decision engine and report are unchanged in shape (FR-2.x, ADR-0001).

**G3 — native matcher and schema are defined, and the Java matcher is not silently reused.** `static/signatures.py` walks only `SCANNED_SUFFIXES = (".java", ".xml")` and matches *text lines* via `_line_matches` — it cannot parse binary `.so` exports/strings. So `native.py` implements its own binary matcher rather than calling the Java matcher, but emits the *same* `Evidence` shape so the decision engine and report treat native and Java matches identically. Native YAML schema (additive to the existing schema in `config/signatures/`, with `pattern_type` narrowed to native-only types so a rule can't load a Java-only type against a binary target):
```yaml
- id: native_jni_root_check
  category: root
  weight: 0.5
  pattern_type: export_symbol   # export_symbol | embedded_string (native-only; Java-only types rejected here)
  patterns:
    - "check_root"
  evidence_type: native_symbol
```
**G3b — `api_call` is NOT a valid pattern type.** `VALID_PATTERN_TYPES = {"string_literal", "class_reference", "regex"}` (`signatures.py`); the previous `# string_literal | api_call | class_reference | regex` comment in this doc's YAML example advertised a type that does not exist and never did. That comment is corrected below. `_line_matches` raises `ValueError` only for a type that passes load — and since `api_call` is rejected at *load* by `_validate_signature_entry`, a rule author choosing it fails loudly before scan, never mid-scan (no silent detection weakening). The native schema above keeps the same load-time rejection discipline: an unknown `pattern_type` in a native rule is a loud load error, not a silent no-op.

**G6 — ABI handling.** An APK typically ships multiple ABIs (`lib/armeabi-v7a`, `arm64-v8a`, `x86_64`, …). `native.py` enumerates all `lib/<abi>/` directories present and records per-ABI coverage. The scan covers *all* ABIs present in the APK (archive enumeration, not the runtime device's ABI) so a device-only scan can't silently under-cover; each ABI is an entry in the coverage contract (G1). A signature present only in one ABI is still a real finding for that ABI, recorded with the ABI in its `file` path.

**G10 — stripped-vs-unstripped `.so`.** A stripped native library has a much smaller export/string surface than its unstripped original; its reduced surface must map to `partial` in the coverage contract, never `fully_analyzed`. `native.py` detects strip state (e.g. absent `.symtab`/symbol-table heuristics) and reports it; the coverage contract uses it to bound how confident a native NEITHER may be.

**G-B — native obfuscation also degrades coverage (closes the N1 asymmetry).** N1's `heavy→partial` rule keys off the Java single-char class ratio — it does not cover native. A native library that is obfuscated but *not* stripped (Obfuscator-LLVM-style renamed/encrypted symbols, encrypted native strings) would otherwise report `fully_analyzed` and produce a confident native NEITHER despite unreliable strings — the same "negative from an under-covered surface" error G10/N1 exist to prevent. So `native.py` emits a native degradation signal mirroring N1 (deterministic heuristics: symbol-entropy, encrypted-string indicators), and the native surface maps to `partial` when it is obfuscated-but-not-stripped, not `fully_analyzed`. This keeps the Java and native coverage rules symmetric (both degrade on obfuscation) so the G-A surface-set exclusion and F2 per-category gating behave consistently across surfaces. Per-ABI, the degradation applies per-library under that ABI (G6).

### Coverage / measurement layer (`static/coverage.py`)
A per-surface contract `fully_analyzed | partial | unscannable` for each analysis surface (Java decompile, native `.so`, manifest/resources). The explicit *bound* of every scan, so a `partial`/`unscannable` surface reads as a lower bound, never a silent confident negative (extends ADR-0006's measured-not-asserted discipline).

**G1 — end-to-end carrier (coverage is not free-floating).** Coverage is a real, persisted signal with a defined path to every consumer:
- **Storage:** a JSON `coverage` column on `RunRecord` (`src/storage/db.py`), serialized as `{surface: "fully_analyzed"|"partial"|"unscannable"}`.
- **Calibration:** a matching `coverage` field on `RunRow` (`src/calibration/types.py`), populated by the same `storage/results.py` adapter that already builds `decompile_completeness`.
- **Report:** a coverage block in both the per-run report and the calibration report's Notes — not hardcoded template text; rendered from the persisted field.
- **Synthesizer interface:** the deferred dynamic synthesizer (group C, items 12-17) reads this per-surface coverage as its *input contract*: it only attempts bypass on surfaces marked `fully_analyzed`, and treats a `partial`/`unscannable` surface as an explicit "no attempt + no confident negative" state. That interface is named here precisely so group C depends on an already-emitted signal.

**G2 — `partial` disambiguation (two meanings, one rule).** Per-surface coverage *coexists* with the existing `decompile_completeness ∈ complete|partial|unknown` (`RunRecord.decompile_completeness`), which stays the single driver of the existing Tier-2 exclusion (`src/calibration/report.py`, `generator.py`). The combination rule (G-C): the Java surface's coverage is *derived from* `decompile_completeness` — `complete→fully_analyzed`, `partial→partial`, `unknown→unscannable` — **modified by the obfuscation rule**: `obfuscation_level == heavy` forces the Java surface to `partial` regardless of `decompile_completeness` (N1). So `Java_surface_coverage = min(decompile_completeness, obfuscation)`. G2's "the two never disagree for the Java surface" holds **only when `obfuscation_level != heavy`**; under `heavy`, the Java surface is `partial` even on an exit-0 complete decompile, and that is the intended exception (a heavy target's encrypted strings aren't reachable, so exit-0 ≠ fully analyzed). A `partial` Java surface + `unscannable` native surface is simply two per-surface states, each with its own bound; the report's Limitations section reads both. `decompile_completeness` is *not* removed or migrated — it remains the backward-compatible signal calibration already keys on; coverage is additive.

**F2 — per-surface Tier-2 semantics (native/manifest coverage must actually gate).** Reporting a `partial`/`unscannable` native or manifest surface but then counting that run's native/manifest NEITHER as a confident TN in Tier 2 would reintroduce exactly the "negative from an under-covered surface is proof of absence" error G2/G10 exist to prevent. So per-surface coverage is not merely cosmetic: the calibration harness's exclusion rule is extended to *any* surface, keyed off the per-surface coverage map (G1). The existing Java path is unchanged (`decompile_completeness` still maps to the Java surface's coverage).

**G-A — per-category surface sets (the exclusion is per-category, not per-surface).** The categories are `root`/`ssl`, and either can be evidenced by multiple surfaces: root by `root_detection.yaml` (Java) *and* `native_detection.yaml` (e.g. `native_jni_root_check`); ssl by `ssl_pinning.yaml` (Java), native, and manifest. So the exclusion is defined per-category over its *governing surface set*:
- `root → {Java, native}`
- `ssl → {Java, native, manifest}`
A category's NEITHER is excluded from Tier 2 if **any** of its governing surfaces is `partial`/`unscannable`. The case that matters: a root check hiding in a stripped `.so` (`native=partial`, `Java=complete`) → the root category is excluded, because Java being fully analyzed doesn't make the root NEITHER confident while the native surface isn't. `fully_analyzed` on *every* governing surface is the only state that can contribute a confident TN/FP. In implementation, `compute_calibration_report` consumes `RunRow.coverage` (G1) and excludes per-category against that category's surface set. Until `native.py`/manifest coverage is actually emitting per-surface states, this rule is a no-op (all surfaces report via the Java-derived default), and Tier-2 behavior is byte-for-byte what it is today — documented, not silently changed.

### Dynamic bypass synthesizer + AI learner (deferred — not spec'd here)
The dynamic bypass synthesizer (group C, items 12-17) and AI baseline + learner (group D, items 18-20) are intentionally **not** spec'd in this doc — deferred to their own low-level designs immediately before each starts (ADR-0003), with the synthesizer's execution behind the sandbox + human-review gate (ADR-0004) and the AI learner's promotion gated on an empirical baseline diff (ADR-0008, G4: bypass-convergence for bypass, precision/recall for detection). This section is reserved as their seam; coverage (G1 above) is their emitted input.

## Dynamic success-check convention

Each analysis target implements a common interface — this is the mechanism that makes Phase 2/3 purely additive (NFR-13):

```python
class SuccessCheck(Protocol):
    def check(self, logcat_output: str, frida_log: str) -> VerificationResult:
        """Returns which categories were confirmed bypassed, with the
        specific evidence line proving it — never a bare boolean."""
```

`uncrackable1.py`, `uncrackable2.py`, `uncrackable3.py` each implement this against that target's specific observable success signal (e.g., a regex match on the revealed secret string, or confirmation that a specific blocking log line did *not* appear where it previously did).

## StageResult convention

Every stage in the pipeline returns this; the orchestrator (a plain function, per ADR-0002) checks `.status` before proceeding to the next stage:

```python
@dataclass
class StageResult:
    stage: str
    status: Literal["success", "failed", "skipped"]
    evidence: dict
    error: str | None
    duration_ms: int
```

A `failed` status halts the pipeline with the full `StageResult` printed/logged — never silently continues (NFR-1). `skipped` is reserved for explicit, intentional skips (e.g., dynamic analysis skipped via `--skip-dynamic`), always logged as such, never conflated with success.

## CLI shape

```
PYTHONPATH=src uv run python -m cli run --apk path/to/target.apk --justification ACADEMIC_TRAINING_TARGET [--skip-dynamic] [--device <serial>] [--target <name>]
PYTHONPATH=src uv run python -m cli calibration-report [--ground-truth path/to/ground_truth.yaml]
```

Phase 4 added the second command (FR-9.2) - Typer's single-command auto-collapse (true for Phases 1-3, when `run` was the only registered command) stopped applying the moment `calibration-report` was added, which broke every hardcoded bare-command invocation that assumed it (`scripts/collect_verification_bundle.py`, `README.md` - both fixed alongside this doc). Revised here rather than left to silently mislead, per this project's evidence-over-assertion discipline.

`--justification` is required on `run` (FR-8.1) - the CLI refuses to run without it, writing the corresponding audit log entry (FR-8.2) before any analysis stage begins (in implementation, this happens right after ingestion resolves the real APK hash, so the audit entry can reference it - ingestion itself isn't gated, since hashing/metadata extraction is identification, not analysis). `calibration-report` takes neither `--apk` nor `--justification` - it reports over an already-audited historical corpus, not a fresh act of analysis.

## Testing approach

Unit tests (pytest, `tests/unit/`) cover `static/signatures.py` and `static/decision_engine.py` with fixture-based inputs (`tests/fixtures/`) — known true-positive snippets, known true-negative snippets, and boundary cases straddling the confidence threshold (NFR-17). These require no Android toolchain and run anywhere `uv` runs. The dynamic/Frida side has no meaningful unit-test surface — its verification is each phase's real end-to-end run against a real target on the reference WSL2 environment, with the resulting report and logs serving as that phase's integration-test record (NFR-18).
