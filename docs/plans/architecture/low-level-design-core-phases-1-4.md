# Low-Level Design — Core Phases 1-4

Concrete, implementation-ready design for the deterministic core. Phases 5-7 stay at the high-level-architecture level of detail until this core is proven and each AI phase's own low-level design is written immediately before it starts (ADR-0003) — writing their low-level design now would be speculative.

The remaining work is organized by *detection surface* per ADR-0008 (technology-based reorganization). This doc specs the deterministic groups — the expanded static core, native `.so` analysis, and the coverage/measurement layer — as implementation-ready design. The gated groups (dynamic bypass synthesizer, AI baseline + learner) are deferred: their own low-level design is written immediately before each starts (ADR-0003), and the synthesizer's execution stays behind the sandbox + human-review gate (ADR-0004) with the AI learner's promotion gated on an empirical baseline diff (ADR-0008).

## WSL2 → Windows Frida bridge (added after real testing on the reference machine)

Windows' ADB server and a Windows-managed emulator's `frida-server` are both only reachable on Windows' own `127.0.0.1`, which WSL2 cannot address directly, and `netsh portproxy` conflicts with `adb forward`. `device.py` resolves this with a small relay: `adb forward` sets up a Windows-local listener, a Python relay process (`scripts/frida_relay.py`) is started on Windows (via `Start-Process` from WSL2) bridging that listener to a port reachable from WSL2 over the Windows host IP, and Frida connects through `add_remote_device()` to that relay instead of `frida.get_device()` directly. `device.setup_frida_connection()` is a no-op passthrough to `frida.get_device()` on native Linux - this whole bridge only activates when actually running under WSL2. Real bugs found and fixed in the first version of this (verified by direct testing, not assumed): a hardcoded personal-machine fallback where Windows-user-directory detection should instead fail loudly; `Get-Process`-based cleanup that never actually matched anything since `CommandLine` isn't populated without elevation (needs `Get-CimInstance Win32_Process` instead); a blind `sleep(3)` replaced with an actual poll-until-listening check.

## Signature YAML schema

```yaml
- id: root_su_binary_check
  category: root
  weight: 0.3
  pattern_type: string_literal   # string_literal | api_call | class_reference | regex
  patterns:
    - "/system/bin/su"
    - "/system/xbin/su"
  evidence_type: bytecode_string

- id: rootbeer_framework
  category: root
  weight: 0.5
  pattern_type: class_reference
  patterns:
    - "com.scottyab.rootbeer"
  evidence_type: bytecode_class
```

Each matched signature contributes its `weight` to a running confidence score per category (`root`, `ssl`), capped at 1.0. Every match records `{signature_id, file, line_or_offset, matched_text}` as evidence — this satisfies FR-2.2/FR-2.3/FR-2.6 and NFR-16 directly: no finding without a citation.

## Decision engine interface

```python
def classify(static_evidence: StaticEvidence) -> ClassificationResult:
    """Deterministic weighted-signature scoring.
    Returns per-category confidence + the full evidence list behind it.
    Threshold (default 0.7) is read from config/settings.yaml, not hardcoded,
    since it needs empirical tuning in Phase 4 against real calibration data.
    """
```

`ClassificationResult` carries `action: ROOT_ONLY | SSL_ONLY | BOTH | NEITHER`, per-category confidence, and the evidence list — everything the report and the calibration recorder need, with nothing hidden behind an opaque score (FR-3, ADR-0001).

## Deterministic roadmap groups (ADR-0008, spec'd here)

These extend the deterministic core; all remain signature/rule work under ADR-0001. Native matches and behavioral indicators are additional *evidence sources*, not a separate decision tier — they feed the same weighted-confidence model.

### Expanded static core
- **Obfuscation indicator** — a per-run `obfuscation_level ∈ clear | light | heavy` derived deterministically (e.g. identifier entropy, presence of `-obfuscate` markers, string-encryption patterns). Reported, not used to silence findings.
- **Behavioral indicators** — string-decryptor stubs, reflection-based string building, crypto primitive usage; each is a matchable signature pattern contributing evidence, so a technique that only appears *behaviorally* (not as a plain literal) is still surfaced with a citation.
- **Manifest / resource analysis** — beyond the existing `network_security_config` read: stored-cert presence, `DevicePolicyManager` usage, and the networkSecurityConfig element itself, matched against the signature set. Every read carries its own coverage state.
- **No silent parse swallows** — every unparseable manifest/resource element surfaces as a `parse_failure` with a byte offset rather than being skipped; a partial parse never presents as a complete scan (ties into the coverage contract below).

### Native `.so` analysis (`static/native.py`)
Parses `.so` export symbols and embedded strings from each native library in the APK, matched by hand-authored native signature rules in `config/signatures/`. Matches record the same `{signature_id, file, line_or_offset, matched_text}` evidence shape and contribute weight to the same per-category confidence — so native root-detection or SSL-pinning logic is scored identically to Java-side logic, and the decision engine and report are unchanged in shape (FR-2.x, ADR-0001).

### Coverage / measurement layer (`static/coverage.py`)
A per-surface contract `fully_analyzed | partial | unscannable` for each analysis surface (Java decompile, native `.so`, manifest/resources). Persisted per run and surfaced in both the per-run report and the calibration report's Notes — the explicit *bound* of every scan, so a `partial`/`unscannable` surface reads as a lower bound, never a silent confident negative (extends ADR-0006's measured-not-asserted discipline). The dynamic bypass synthesizer and AI learner (roadmap groups 12-20) are intentionally **not** spec'd here — deferred to their own low-level designs immediately before they start (ADR-0003), with the synthesizer's execution behind the sandbox + human-review gate (ADR-0004) and the AI learner's promotion gated on an empirical baseline diff (ADR-0008).

## Dynamic success-check convention

Each analysis target implements a common interface — this is the mechanism that makes Phase 2/3 purely additive (NFR-13):

```python
class SuccessCheck(Protocol):
    def check(self, logcat_output: str, frida_log: str) -> VerificationResult:
        """Returns which categories were confirmed bypassed, with the
        specific evidence line proving it — never a bare boolean."""
```

`uncrackable1.py`, `uncrackable2.py`, `uncrackable3.py` each implement this against that target's specific observable success signal (e.g., a regex match on the revealed secret string, or confirmation that a specific blocking log line did *not* appear where it previously did).

## StageResult convention

Every stage in the pipeline returns this; the orchestrator (a plain function, per ADR-0002) checks `.status` before proceeding to the next stage:

```python
@dataclass
class StageResult:
    stage: str
    status: Literal["success", "failed", "skipped"]
    evidence: dict
    error: str | None
    duration_ms: int
```

A `failed` status halts the pipeline with the full `StageResult` printed/logged — never silently continues (NFR-1). `skipped` is reserved for explicit, intentional skips (e.g., dynamic analysis skipped via `--skip-dynamic`), always logged as such, never conflated with success.

## CLI shape

```
PYTHONPATH=src uv run python -m cli run --apk path/to/target.apk --justification ACADEMIC_TRAINING_TARGET [--skip-dynamic] [--device <serial>] [--target <name>]
PYTHONPATH=src uv run python -m cli calibration-report [--ground-truth path/to/ground_truth.yaml]
```

Phase 4 added the second command (FR-9.2) - Typer's single-command auto-collapse (true for Phases 1-3, when `run` was the only registered command) stopped applying the moment `calibration-report` was added, which broke every hardcoded bare-command invocation that assumed it (`scripts/collect_verification_bundle.py`, `README.md` - both fixed alongside this doc). Revised here rather than left to silently mislead, per this project's evidence-over-assertion discipline.

`--justification` is required on `run` (FR-8.1) - the CLI refuses to run without it, writing the corresponding audit log entry (FR-8.2) before any analysis stage begins (in implementation, this happens right after ingestion resolves the real APK hash, so the audit entry can reference it - ingestion itself isn't gated, since hashing/metadata extraction is identification, not analysis). `calibration-report` takes neither `--apk` nor `--justification` - it reports over an already-audited historical corpus, not a fresh act of analysis.

## Testing approach

Unit tests (pytest, `tests/unit/`) cover `static/signatures.py` and `static/decision_engine.py` with fixture-based inputs (`tests/fixtures/`) — known true-positive snippets, known true-negative snippets, and boundary cases straddling the confidence threshold (NFR-17). These require no Android toolchain and run anywhere `uv` runs. The dynamic/Frida side has no meaningful unit-test surface — its verification is each phase's real end-to-end run against a real target on the reference WSL2 environment, with the resulting report and logs serving as that phase's integration-test record (NFR-18).
